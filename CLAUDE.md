## Project Structure

This repository is an OXID eShop module that runs within the OXID Docker SDK environment.

```
/path/to/oxid-sdk/                            <- OXID SDK root
├── Makefile                                  <- SDK commands (make up, make down, etc.)
├── docker-compose.yml                        <- Generated by setup
├── .env                                      <- Generated by setup
├── containers/                               <- Container configurations
├── services/                                 <- Service definitions (php, mysql, etc.)
└── source/                                   <- THIS MODULE (mounted to /var/www in container)
    ├── src/                                  <- Module source code
    ├── tests/                                <- Test suites
    ├── metadata.php                          <- Module metadata
    ├── composer.json                         <- Module dependencies & scripts
    ├── bin/personalize.sh                    <- Personalization script
    └── recipes/setup-development.sh          <- Full environment setup
```

**Key Points**:
- Commands starting with `make` run from SDK root (`../`)
- The `source/` directory is mounted as `/var/www/` inside the PHP container
- Quality/testing tools (defined in `composer.json` scripts) run from SDK root using: `docker compose exec -T php composer [script-name]`

## Two Distinct Workflows

### Detecting Which Phase You're In

Check if personalization is needed by looking for these indicators:
- Package name in `composer.json` is `oxid-esales/module-template`
- Namespace is `OxidEsales\ModuleTemplate`
- Module ID in `metadata.php` is `oe_moduletemplate`
- Title contains "OXID eSales Module Template (OEMT)"
- `bin/personalize.sh` file still exists
- TODO comments throughout the codebase

If ANY of these are true → **Use Workflow 1 (Initial Personalization)**
If NONE of these are true → **Use Workflow 2 (Development)**

## Workflow 1: Initial Personalization (ONE-TIME ONLY)

This workflow is used **only once** when transforming the module-template into your own module.

### Prerequisites
- Docker and Docker Compose installed
- Entry in `/etc/hosts`: `127.0.0.1 localhost.local`
- OXID SDK cloned to project root
- Module template cloned to `source/` directory

### Step 1: Personalize the Module

**Location**: Run from `source/` directory

```bash
cd source
./bin/personalize.sh
```

The script will prompt for:
- **Package name** (original: `oxid-esales/module-template`)
  - Enter your package name in lowercase format: `vendor/package-name`
- **Namespace** (original: `OxidEsales\ModuleTemplate`)
  - Enter your namespace in PascalCase format: `Vendor\PackageName`
- **Module ID** (original: `oe_moduletemplate`)
  - Enter your module ID: alphanumeric + underscore, e.g., `vendor_packagename`
- **Company name** (original: `OXID eSales AG`)
  - Enter your company name for file headers

**What it modifies**:
- `composer.json` - package name, namespaces
- `metadata.php` - module ID, title reset to v1.0.0
- All source files - namespace declarations
- `.github/oxid-esales/module-template.yaml` - CI configuration (sets TODO markers)
- `migration/migrations.yml` - migration configuration
- `CHANGELOG.md` - resets to v1.0.0
- `LICENSE` - clears content (TODO marker)

### Step 2: Manual TODO Cleanup

After personalization, search for "TODO" keywords and replace them with appropriate values.

**Claude Code can help**: Ask Claude to:
- Search for all TODO markers in the codebase
- Review each one with you and suggest replacements
- Check for any other personalization items that might have been missed (e.g., example code, placeholder values)

Files typically containing TODOs after personalization:
- `metadata.php` - Update module title
- `.github/oxid-esales/module-template.yaml` - SonarCloud project key, organization, repository URL
- `LICENSE` - Add your license text
- `README.md` - Update project description, badges, documentation

**After completing Steps 1 & 2**: The personalization script (`bin/personalize.sh`) can be removed as it's no longer needed.

### Step 3: Initial Development Environment Setup

**Location**: Run from `source/` directory

**Before running**: Review and adjust `recipes/setup-development.sh` for:
- **Shop branch version** (currently set to b-7.4.x) - verify this matches your target OXID version
- **PHP version** (currently set to 8.2) - confirm compatibility with your OXID version
- **MySQL version** (check if matches your requirements) - may need adjustment

**Claude Code can help**: Ask Claude to check the setup-development.sh file and verify versions are correct for your needs.

> ⚠️ **IMPORTANT - For Claude Code**:
> **DO NOT attempt to run the `setup-development.sh` script yourself.** This script is complex and performs multiple SDK configuration steps that are difficult to monitor and debug remotely.
>
> Instead:
> - Help the developer review and modify the script if needed (e.g., adjust versions, paths, or configuration)
> - Explain what the script does and answer questions about it
> - **Ask the developer to run the script themselves** and provide you with any output or errors they encounter
> - After they run it, you can help troubleshoot any issues based on their feedback

```bash
# Setup the complete development environment (from source/ directory)
# DEVELOPER: Please run this command yourself (not Claude)
./recipes/setup-development.sh -e CE    # or -e EE for Enterprise Edition
```

**What this does** (runs from SDK root context):
1. SDK setup: `make setup && make addbasicservices`
2. Adds services: adminer, selenium-chrome, node
3. Configures PHP and MySQL versions, Apache (source/source/ path)
4. Builds and starts containers
5. Installs OXID eShop CE/EE (dev-b-7.4.x by default)
6. Installs Twig components and apex theme
7. Sets up database (no demodata)
8. Installs and activates the module
9. Runs migrations
10. Creates admin user (noreply@oxid-esales.com / admin)

**Access after setup**:
- Shop: http://localhost.local
- Admin: http://localhost.local/admin (noreply@oxid-esales.com / admin)
- Adminer: http://localhost.local:8080 (server: mysql, root/root)
- Mailpit: http://localhost.local:8025

## Workflow 2: Development (ONGOING)

This is the normal development workflow used after personalization is complete.

### Environment Management

**Start the environment** (from SDK root):
```bash
cd ..               # Go to SDK root (if in source/)
make up             # Start all containers
```

**Stop the environment**:
```bash
cd ..               # Go to SDK root
make down           # Stop all containers
```

**Connect to containers**:
```bash
cd ..               # Go to SDK root
make php            # Connect to PHP container (bash shell)
make node           # Connect to Node container (bash shell)
```

### Quality Tools

**Run from SDK root** (`../`):

```bash
# Code quality checks
docker compose exec -T php composer phpcs          # Check coding standards (PSR-12)
docker compose exec -T php composer phpcbf         # Auto-fix coding standards
docker compose exec -T php composer phpstan        # Static analysis (level 8)
docker compose exec -T php composer phpmd          # Mess detector
docker compose exec -T php composer static         # Run all static analysis tools

# Generate reports (for CI)
docker compose exec -T php composer phpcs-report
docker compose exec -T php composer phpstan-report
docker compose exec -T php composer phpmd-report
```

### Testing

**Run from SDK root** (`../`):

#### Unit Tests (no shop dependencies)
```bash
docker compose exec -T php composer tests-unit

# Run single test
docker compose exec -T php vendor/bin/phpunit --config=tests/ --testsuite=Unit --filter testMethodName

# With coverage
docker compose exec -T php bash -c "XDEBUG_MODE=coverage vendor/bin/phpunit --config=tests/ --testsuite=Unit --coverage-html=tests/Reports/CoverageHtml"
```

#### Integration Tests (requires shop)
```bash
docker compose exec -T php composer tests-integration

# Run single test
docker compose exec -T php vendor/bin/phpunit --bootstrap=/var/www/source/bootstrap.php --config=tests/ --testsuite=Integration --filter testMethodName
```

#### Acceptance Tests (Codeception - frontend tests)
```bash
docker compose exec -T php composer tests-codeception

# Run specific test
docker compose exec -T php bash -c "THEME_ID=apex MODULE_IDS=[your_module_id] SHOP_ROOT_PATH=/var/www vendor/bin/codecept run Acceptance -c tests/codeception.yml [TestName]"
```

#### All Tests
```bash
docker compose exec -T php composer tests-all
```

**Test outputs**:
- Reports: `source/tests/Reports/`
- Codeception screenshots/HTML: `source/tests/Codeception/_output/`

### Module Management

**Run from SDK root** (`../`):

```bash
# Install module
docker compose exec -T php vendor/bin/oe-console oe:module:install ./

# Activate/deactivate module
docker compose exec -T php vendor/bin/oe-console oe:module:activate [your_module_id]
docker compose exec -T php vendor/bin/oe-console oe:module:deactivate [your_module_id]

# Run migrations
docker compose exec -T php vendor/bin/oe-eshop-doctrine_migration migrations:migrate [your_module_id]

# List migrations status
docker compose exec -T php vendor/bin/oe-eshop-doctrine_migration migrations:status [your_module_id]

# Regenerate database views (after schema changes)
docker compose exec -T php vendor/bin/oe-eshop-db_views_generate

# Reset database
docker compose exec -T php vendor/bin/oe-console oe:database:reset --db-host=mysql --db-port=3306 --db-name=example --db-user=root --db-password=root --force

# Create admin user
docker compose exec -T php vendor/bin/oe-console oe:admin:create-user --admin-email admin@oxid-esales.com --admin-password admin
```

### Working with Composer

**Run from SDK root** (`../`):

```bash
# Update dependencies
docker compose exec -T php composer update --no-interaction

# Install dependencies
docker compose exec -T php composer install --no-interaction

# Clear cache
docker compose exec -T php composer clear-cache
```

## Architecture Overview

### Module Structure
- **src/**: Module source code (PSR-4 autoloading based on your namespace)
- **tests/**: Test suites
  - **Unit/**: PHPUnit unit tests (isolated, no dependencies)
  - **Integration/**: PHPUnit integration tests (requires shop)
  - **Codeception/**: Acceptance tests (browser-based frontend tests)
- **migration/**: Doctrine migrations
  - **migrations.yml**: Configuration (table name, namespace, paths)
  - **data/**: Migration files
- **metadata.php**: Module metadata (id, title, version, extend)
- **services.yaml**: Symfony DI container services (autowire enabled)
- **composer.json**: Package definition, autoloading, scripts

### OXID eShop Integration

**Module metadata** (`metadata.php`):
- Module ID, title, version, author
- Extended classes (class chain) - define in 'extend' array
- Settings, blocks, events

**Dependency Injection** (`services.yaml`):
- Define services with autowiring enabled by default
- Public: false by default
- Access via container in controllers/services

**Class Extension**:
- Use `extend` in metadata.php to extend shop classes
- Namespaced classes only (OXID 7.x)

**Database Migrations**:
- Migration table name pattern: `oxmigrations_[your_module_id]`
- Run via `oe-eshop-doctrine_migration` wrapper
- Required for module installation/updates
- Must be idempotent (safe to rerun)

> ⚠️ **CRITICAL**: Never read or access files from:
> - `vendor/oxid-esales/oxideshop-pe/` (Professional Edition - proprietary)
> - `vendor/oxid-esales/oxideshop-ee/` (Enterprise Edition - proprietary)
>
> These contain proprietary OXID code. Only Community Edition (`oxideshop-ce`) and module code in `src/` are safe to read.

### Quality Tool Configuration

- **PHPStan**: `tests/PhpStan/phpstan.neon`
  - Level 8 (strictest)
  - Stubs for shop classes in `tests/PhpStan/stubs/`
  - Bootstrap: `tests/PhpStan/phpstan-bootstrap.php`

- **PHPCS**: `tests/phpcs.xml`
  - PSR-12 based
  - Excludes vendor, tests/Reports

- **PHPMD**: `tests/PhpMd/standard.xml`
  - Custom ruleset for OXID modules

- **PHPUnit**: `tests/phpunit.xml`
  - Separate Unit/Integration suites
  - Coverage for `src/` directory

### GitHub Actions

**Workflow**: `.github/workflows/trigger.yaml`
- Triggers on push/PR to configured branches
- Uses OXID's universal workflow (v5)
- Configuration: `.github/oxid-esales/module-template.yaml`

**What runs**:
1. Quality tools (phpstan, phpmd, phpcs)
2. Unit tests
3. Integration tests
4. Acceptance tests (Codeception)
5. SonarCloud analysis

**Secrets needed** (configure in GitHub repository settings):
- `SONAR_TOKEN` - SonarCloud authentication
- Other secrets inherited from OXID workflows

## Development Best Practices

### Testing Strategy
- **Unit tests**: Fast, isolated, no shop dependencies - test business logic
- **Integration tests**: Test shop integration points, database interactions, module activation
- **Codeception tests**: Validate frontend behavior, use HTML ids for selectors
- Aim for high coverage on business logic (unit tests)
- Use Codeception sparingly (slower, but catches frontend issues)

### Codeception Tests
- Add `id` attributes to HTML elements for reliable selection
- Screenshots/HTML saved to `tests/Codeception/_output/` on failure
- Test on Enterprise Edition when possible (shop-aware features)

### Shop Compatibility
- Module should work on CE, PE, EE
- Document any compatibility issues or special requirements
- Skip `@group quarantine` tests (unstable)

### Migrations
- Always idempotent (safe to rerun)
- Test on fresh database before committing
- Document breaking changes in CHANGELOG.md
- Use descriptive migration class names

### Git Workflow
- Commit hooks installed automatically (`.github/commit-hooks`)
- Pre-commit runs quality tools
- Branch naming pattern: `{base-branch}-{description}-{task-number}`
  - Example: `b-7.3.x-add-user-preferences-OXDEV-123`
  - Base branch is typically the current main branch (e.g., b-7.3.x, b-7.4.x)
- **IMPORTANT**: Do not mention "Claude" or "Claude Code" in commit messages
  - Commit messages should be tool-agnostic and professional
  - Focus on what was changed and why, not which tool was used

### Namespace and Autoloading
- PSR-4 autoloading: Your namespace maps to `src/`, test namespace to `tests/`
- Adding new classes under existing namespaces requires no additional setup
- Only if you add/change PSR-4 namespace mappings in `composer.json`, run: `docker compose exec -T php composer dump-autoload`

## Troubleshooting

### Container Issues
```bash
cd ..               # SDK root
make down           # Stop everything
make up             # Restart
```

### Module Not Activated
```bash
# From SDK root
docker compose exec -T php vendor/bin/oe-console oe:module:activate [your_module_id]
docker compose exec -T php vendor/bin/oe-eshop-doctrine_migration migrations:migrate [your_module_id]
docker compose exec -T php vendor/bin/oe-eshop-db_views_generate
```

### Composer Issues
```bash
# From SDK root
docker compose exec -T php composer clear-cache
docker compose exec -T php composer update --no-interaction
```

### Permission Issues
- SDK syncs users/groups with host (see `.env`)
- Files created in containers should have correct ownership
- If you encounter permission problems, check `HOST_USER_ID` and `HOST_GROUP_ID` in `.env`

### XDebug Configuration
- XDebug 3 preconfigured for remote debugging
- Configure PHPStorm:
  - CLI Interpreter: Docker Compose (php service)
  - Server mapping: `source:/var/www/`
  - Port: 9003 (XDebug 3 default)

### Database Access
- **Adminer**: http://localhost.local:8080
  - Server: `mysql`
  - Username: `root`
  - Password: `root`
  - Database: `example`

### View Logs
```bash
cd ..               # SDK root
docker compose logs -f php      # PHP logs
docker compose logs -f apache   # Apache logs
docker compose logs -f mysql    # MySQL logs
```

### Creating Database Migrations
```bash
# From SDK root
docker compose exec -T php vendor/bin/oe-eshop-doctrine_migration migrations:generate [your_module_id]
# Edit the generated file in source/migration/data/
```

## Environment Variables

**SDK (.env in SDK root)**:
- `PHP_VERSION` - PHP version (8.2 recommended for OXID 7.3.x/7.4.x)
- `MYSQL_VERSION` - MySQL version (5.7 or 8.0)
- `MYSQL_ROOT_PASSWORD` - root password (default: root)
- `MYSQL_DATABASE` - database name (default: example)
- `HOST_USER_ID`, `HOST_GROUP_ID` - Synced with your system user for proper file permissions
- Various port mappings (see `.env.dist` for full list)

**Module**: No .env file required; uses shop configuration from `/var/www/source/`

## Important File Paths

**On your host machine**:
- `../` - SDK root (where Makefile and docker-compose.yml live)
- `./` or `source/` - Module directory (this repository)
- `source/vendor/` - Composer dependencies (OXID shop, packages)

**Inside PHP container** (`/var/www/` maps to `source/` on host):
- `/var/www/` - Module root
- `/var/www/source/` - OXID shop installation
- `/var/www/source/bootstrap.php` - Shop bootstrap (for integration tests)
- `/var/www/vendor/` - Composer dependencies
